# Тёплый сервис Laya: быстрый ответ в протоколе Живого Кода

Сервис держит решающую модель Laya в RAM и обслуживает вызовы без перезагрузки чекпоинта.
Мост `laya_bridge.py` ходит в него прозрачно: если сервис не поднят — падает обратно на
локальный запуск, ничего не ломая.

## Замеры (27 сен 2026, CPU, узел 16 ядер / 15 ГБ)

| Режим | Холодный запуск | Через сервис |
|---|---|---|
`ui_gate` | 6.9 с (из них ~5 с загрузка чекпоинта) | **0.36 с** |
`verdict` | ~7 с | **0.19 с** |
`score`, 10 строк | ~10 с | **0.71 с** |
Второй вызов подряд | — | **0.18 с** |
Время загрузки модели в сервис | — | 4.6–7.4 с |

Вывод из вызова после выгрузки: **0.54 с** (чекпоинт остаётся в page cache ОС).

## API (только localhost)

| Метод | Точка | Смысл |
|---|---|---|
GET | `/health` | `loaded`, `rss_mb`, `idle_s`, `unload_in_s`, счётчики, `pid` |
POST | `/call` | `{"argv":[...], "text":"..."}` или `{"mode":"ui_gate","text":"..."}` |
POST | `/ui_gate`, `/triage`, `/verdict`, `/score`, `/raw` | короткие формы |
POST | `/warm` | принудительно прогреть |
POST | `/unload` | принудительно выгрузить (мгновенно освобождает ~1.2 ГБ) |

Ответ содержит `ok`, `rc`, `result` (разобранный JSON моста), `stdout` (как печатал бы
локальный запуск), `took_ms`, `rss_mb`.

## Политика памяти (требование владельца)

Модель живёт в памяти, пока есть работа; при простое больше `LAYA_IDLE_UNLOAD_S`
(по умолчанию **7200 с = 2 часа**) — выгружается и возвращает ОС ~1.2 ГБ. Следующий
запрос поднимает её лениво. Проверено на 60-секундном пороге: `loaded=false`,
RSS 1734 → 495 МБ, `unloads=1`, затем автоподъём `loads=2` и вызов 0.18 с.

Переменные: `LAYA_IDLE_UNLOAD_S`, `LAYA_PRELOAD`, `LAYA_PORT` (8731), `LAYA_THREADS`,
`LAYA_DEVICE`, `LAYA_MODEL_DIR`, `LAYA_LOCK_WAIT_S`, `LAYA_MLOCK`.

## Управление

```bash
systemctl --user status  laya-warm       # состояние
systemctl --user restart laya-warm       # применить изменения
curl -s localhost:8731/health            # телеметрия
venvs/laya/bin/python orchestration/scripts/laya_bridge.py ui_gate --file in.txt   # тёплый путь
... --no-service                         # принудительно локальный путь (для сверки)
LAYA_WARM=0 ...                          # то же через переменную
```

Юнит-файл — в репозитории: `orchestration/systemd/laya-warm.service` (симлинк в
`~/.config/systemd/user/`). `Restart=always`, `linger` включён — сервис живёт без сессии.

## Грабли, на которые уже наступили (не повторять)

1. **Самовызов через мост — вечное зависание.** Сервис исполняет родной `main()` моста;
   после того как в мост добавили поход в тёплый сервис, вложенный вызов стал уходить по
   HTTP обратно в сервис и ждать сам себя на `LOCK`: `POST /call` висел бесконечно,
   `calls` не рос, в журнале — `BrokenPipeError`. Лечится заслонкой: сервис добавляет
   вложенному вызову `--no-service` и выставляет `LAYA_IN_SERVICE=1`, мост по этому
   признаку не идёт в сервис повторно. **Явный признак этой поломки: GET работает
   мгновенно, любой POST висит, счётчик вызовов не растёт.**
2. **`MemoryHigh` в cgroup — убийца скорости.** При мягком лимите ядро вытесняет веса, и
   каждый вызов заново читает чекпоинт: наблюдались 9217 major page faults и 300+ с на
   вызов. Мягкие лимиты для такого сервиса не ставить; защищать резиденцию через
   `MemoryMin` (memory.low), а не через потолок.
3. **`Router` ленив.** Конструктор не читает safetensors: после создания RSS всего ~216 МБ.
   Тёплый сервис обязан сделать настоящий `predict` при прогреве, иначе первую живую
   нагрузку встретит холодная загрузка.
4. **`mlockall` упирается в ENOMEM** (torch резервирует большие арены): мандат `mlock` в
   юните оставлен, но резиденцию защищает `MemoryMin=2G`.
5. **`nohup` не спасает.** Процессы, запущенные из сессии агента, умирают вместе с её
   бэкендом; тяжёлое поднимать только через `systemd-run --user` / юниты.

## Диагностика

```bash
journalctl --user -u laya-warm -f                    # прогрев, выгрузки, медленные вызовы
curl -s localhost:8731/health | python3 -m json.tool
```

Признак проблем с памятью у сервиса — рост `rss_mb` без выгрузок и «медленный вызов» в
журнале (> 30 с). Тогда смотреть `orchestration/ORCHESTRATION_MEMORY.md`.
