# Протокол Живого Кода — полная эксплуатационная документация

**Ревизия: 21.11.2026 (коммиты серии `33a8500`…`48e4208`)**
**Репозиторий:** `DarkPushkin/living-code` (private) + зеркало `backup` на внешнем диске F2DB-14E5.

---

## 1. Что это такое

Живой Код — замкнутый автономный конвейер, в котором проекты развиваются **спринтами по расписанию**, каждый спринт проходит **многослойную проверку качества**, а сам конвейер тоже эволюционирует: код, который выполняет эволюцию, сам является предметом эволюции (слой Meta-Evolver).

```
   ┌─────────────────────────────────────────────────────────────────┐
   │                     КОЛЬЦО ЖИВОГО КОДА                          │
   │                                                                 │
   │  Кодер (часовой слот) ──[TRIGGER_AUDITOR]──► Аудитор             │
   │        ▲                                     │                  │
   │        │                          [TRIGGER_LORD]                │
   │        │                                     ▼                  │
   │  Продюсер ◄──[TRIGGER_PRODUCER]── Владыка (вердикт:             │
   │    (релиз)                        ГОРЯЧИЙ/ХОЛОДНЫЙ/ВЕРНУТЬ)    │
   │        │                                     │                  │
   │        └────── cycle_close.py ◄── l3_critic ─┘                  │
   │                                                                 │
   │  Супервизор (часовой) — здоровье всего кольца, тихий режим       │
   │  Инквизитор/Критик — независимая перепроверка                    │
   │  Meta-Evolver — улучшение самого конвейера                       │
   └─────────────────────────────────────────────────────────────────┘
```

Все межролевые связи — **не прямые вызовы LLM**, а маркеры в общем журнале `agents/journal.md` + триггер-кроны. Это детерминированный протокол, LLM занят только внутри ролей.

## 2. Кодеры: часовые слоты, строго по очереди

Четыре активных проекта: `Project1..Project4` (директории `~/LivingCode/ProjectN`, у каждого свой git).

| Джоб | Расписание | Слот | Движок |
|---|---|---|---|
| `LV-coder-project1` | `0 */4 * * *` | час 0 каждых 4 ч | **локальный** `qwen35-coder-vulkan` |
| `LV-coder-project2` | `1 */4 * * *` | час 1 | локальный |
| `LV-coder-project3` | `2 */4 * * *` | час 2 | локальный |
| `LV-coder-project4` | `3 */4 * * *` | час 3 | локальный |

Жёсткие ограничения слота:
- `cron.script_timeout_seconds = 3600` — весь слот не длиннее часа;
- `LIVING_CODE_CRON_BUDGET=3480` в враппере — агенту оставляют 2 минуты на отчёт;
- Спринт обязан быть **умеренным**: в час должны влезть и работа кодера, и весь стек проверки. Кодер не перегружает себя объёмом, чтобы не задерживать очередь.

Локальная модель: llama.cpp + Vulkan, порт 8082, модель `qwen3.5-4B-super-coder.Q4_0.gguf`, контекст **262144** (исправление шторма «Conversation too long»), `--reasoning off` (баг пустых ответов). Автозапуск: user-systemd юнит + `linger` — поднимается после ребута без логина.

## 3. Маршрутизация моделей

| Группа | Модель / провайдер |
|---|---|
| Только 4 кодера | `qwen35-coder-vulkan` / custom (llama.cpp :8082) |
| Все остальные роли (аудит, владыка, инквизитор, продюсер, супервизор, критик, поисковик, профессор, медиа…) | `mistralai/mistral-large-4-1t-a52b` / nvidia (облако) |
| Запасная облачная модель (хвост цепочки фолбэков) | `minimaxai/minimax-m3.1-flash` / nvidia (MiniMax M3.1 Flash) |

Враппер `living_code_agent_wrapper.py` перебирает модели из `FREE_POOL` при 429/ошибках; ретрай rc=75 (неизвестный исход) логируется маркером `[RC75_RETRY]` в journal.

## 4. Стек проверки качества (облако)

Trigger-only джобы (`once at 2099-01-01`, взводятся врапперами через `resume --run-now`):

| Джоб | ID | Враппер | Что делает |
|---|---|---|---|
| `LV-auditor` | `7924c46d8dbf` | `wrapper_auditor.sh` | Аудит свежего спринта |
| `LV-lord-of-code` | `80487bc08a9c` | `wrapper_lord_of_code.sh` | Вердикт Владыки: ГОРЯЧИЙ/ХОЛОДНЫЙ/ВЕРНУТЬ |
| `LV-producer` | `90f76ccbbdab` | `wrapper_producer.sh` | Релизная сборка ГОРЯЧИХ |

Цепочка жёстко привязана по ID: кодер → аудитор → владыка → продюсер. Если джоб пересоздаётся (новый ID) — `NEXT_JOB_ID` в врапперах надо перевязать (это и было причиной разрыва цепи 20–21.11).

Периодические проверяющие: `LV-inquisitor` (`35 * * * *`), `LV-critic`, `LV-super-supervisor` (`0 * * * *`).

**Гейт доказательств** (`evidence_gate.py`): любой отчёт, заявляющий готовность без указания проверенных артефактов, помечается `NOT_VERIFIED` и уходит как FAIL — «работает на словах» не проходит.

**l3_critic**: для ГОРЯЧИХ проектов детерминированно проверяет deliverable против критериев; только `stabilen` + чистый git разрешают авто-релиз.

## 5. Супервизор: тихий режим

`supervisor_cron.py` каждый час:
1. Проверяет кроны кодеров (`project1-4`): существование, `last_status`, `failure_streak`;
2. Проверяет git-чистоту `~/LivingCode/ProjectN`;
3. Гейт замороженных проектов (FROZEN → крон на паузу);
4. Читает journal **только после своей последней метки** `[SUPER-SUPERVISOR …]` — старые триггеры не считаются новыми;
5. При ГОРЯЧИЙ + stabilen + чистый git → `trigger_producer`.

**Тихий режим:** если нет проблем, вердиктов и триггеров — отчёт в топик 252 НЕ шлётся, пишется одна строка в journal. Спам убран: прежний супервизор ежечасно докладывал ложные «крон не найден» по мёртвым именам проектов.

## 6. Журналы и сигнализация

| Артефакт | Путь | Что в нём |
|---|---|---|
| Общий журнал протокола | `agents/journal.md` | `[TRIGGER_*]`, `[SND_DONE]`, `[SUPER-SUPERVISOR]`, `[RC75_RETRY]`, вердикты |
| Отчёты ролей | `reports/<role>-YYYYMMDD-HHMM.md` | MD-документ на каждый прогон |
| Inference-логи | `orchestration/logs/inference/attempt_*.json` | модель, провайдер, calls, tokens, failed — честный учёт |
| Крон-выводы | `~/.hermes/cron/output/<job_id>/*.md` | полный ответ агента + traceback при сбое |
| Реестр крон | `~/.hermes/cron/jobs.json` → зеркало `orchestration/jobs/jobs.json` | источник правды по расписаниям/моделям |

**Доставка отчётов:** каждый враппер по завершении (успех/провал/квота) вызывает `deliver_role_digest` → ровно один MD-документ в Telegram **топик 252** (`telegram:-1004431090317:252`) через Cathedral Bot API. Токен: `~/.hermes/secrets/cathedral_bot_token` (600, вне git). Текстовые отчёты запрещены — только файлы, с блоками «СДЕЛАНО ЗА ЧАС / ПЛАН / ИЗМЕНЕНИЯ В КОДЕ / ПРОВЕРКА КОДА».

## 7. Laya — детерминированный скорер

`laya_service.py` (порт 8731, CPU) держит прогретый Router-скорер: оценивает тексты/ответы баллом качества + `answer_confidence` (`laya_scores.json`). Холодный старт ~4.6 с, прогретый — миллисекунды. Политика памяти: выгрузка после 2 ч простоя (`LAYA_IDLE_UNLOAD_S=7200`), ленивый прогрев по следующему запросу. Laya — не LLM: это быстрый измеритель, снимающий с облачных ролей часть «стоит ли это внимания».

## 8. Мутации и эволюция плана

- **`EVOLUTION_PLAN*.md`** — живой план эволюции: актуальная ревизия указывается в шапке `EVOLUTION_PLAN.md`; старые ревизии архивируются с датой. План переписывается по итогам циклов (Владыка/Продюсер/Профессор), а не «навсегда».
- **`meta_evolver.py`** — третий слой архитектуры A-Evolve: анализирует `living_code_agent_wrapper.py`, `cycle_close.py`, `l3_critic.py` по проблемам, найденным критиком и кодерами, и готовит改良-коммиты **в репозиторий самого конвейера**: новая ветка + коммит + уведомление Владыке на ревью. Так эволюционирует сам механизм эволюции.
- **`check_roster.py`** — гейт целостности: сверяет реестр крон с ожидаемым ростером ролей, валидирует пары model/provider. Любая ручная правка реестра без зеркала и гейта = рассинхрон.

## 9. Отказоустойчивость

| Сбой | Поведение |
|---|---|
| Модель зависла | `HERMES_CRON_TIMEOUT=3000` (вотчдог agent-джобов, `~/.hermes/.env`); скриптовые слоты — 3600 s |
| 429 квота | Перебор FREE_POOL с backoff, метка сброса квоты |
| rc=75 (неизвестный исход) | Авто-ретрай + `[RC75_RETRY]` в journal; следующая роль не триггерится |
| Ребут хоста | llama.cpp поднимается systemd+linger; кроны — Hermes scheduler с `catch_up_missed` |
| Падение отчётности | Отчёт о провале тоже шлётся в 252 — «молчаливого» слота не бывает |

## 10. Правила внесения изменений (для агентов)

1. Модели/расписания — только через `hermes cron edit/create`, затем зеркало `jobs/jobs.json` + `check_roster.py` (гейт должен быть зелёным).
2. Врапперы — в `~/.hermes/scripts/wrappers/` (симлинк на `orchestration/scripts/wrappers/`); после правки `bash -n`.
3. Пересоздание trigger-only джоба → перевязать все `NEXT_JOB_ID`, ссылавшиеся на старый ID.
4. Коммит в `orchestration` + `git push origin HEAD:main` + `git push backup HEAD:main` по готовности.
5. Секреты — только `~/.hermes/secrets/` (600). В git — никогда.

## Аудит 21.11.2026: почему пайплайн «не работал» и что исправлено

| # | Симптом | Корневая причина | Исправление |
|---|---------|-------------------|-------------|
| 1 | `Script timed out after 3600s` у кодеров/Владыки | `subprocess.run(capture_output=True)` убивал только прямого потомка, а пайп держали его внуки → `communicate()` висел до 3600s | `_run_group_timeout()`: `start_new_session` + SIGKILL по всей группе; доказано тестом `scripts/test_timeout_group.py` (rc=124 за 5.0s, выживших нет) |

| 5 | Релизов нет ни за месяц | Стадии промоушена не было: `promotion_check()` только перечислял кандидатов; проекты не переносились в `CompleteProjects`, очередь не пополнялась | Новый `scripts/promote_check.py` + `scripts/generate_state.py` + cron `LV-promote-check` (часовая, `:10`) |
| 6 | Конвейер «не видит» проекты кодеров | У `Project1–4` не было `STATE.json`; в `Projects/` лежали другие 12 проектов | `generate_state.py` считает completion по чекбоксам `PLAN.md`, hot_files по `git status` |
| 7 | Владыка никогда не выпускал проект | Промпт требовал строку `ВЕРДИКТ` только в ветке возврата; в ветке успеха её не было | Промпт Владыки: в успехе обязательна строка `ВЕРДИКТ: ProjectN — ГОРЯЧИЙ` |
| 8 | `LV-harness-opt` interrupted ×3 | Агентский джоб без враппера: нет бюджета/таймаута/фолбэков движка | Остаётся единственным агентским джобом — переведён на общий watchdog (см. ниже) |

Правило, которое стоит за всей таблицей: **слот обязан укладываться в окно с запасом на отчёт,
коммит и доставку.** Бюджет 3480s при `script_timeout_seconds=3600` — это не «медленно»,
это гарантированная потеря работы: крон убивал слот между моделью и коммитом
(в `Project2/3/4` оставались незакоммиченные файлы).

## Конвейер проектов (схема владельца, 21.11.2026)

| Папка | Роль |
|-------|------|
| `LivingCode/Projects/` | **Очередь** проектов. Отсюда берётся следующий проект. |
| `LivingCode/CompleteProjects/` | **Выпущенные** проекты: 100% холодный код + финальная сопроводительная документация (`ФИНАЛЬНОЕ_ДОСЬЕ.md`). |
| `LivingCode/Project1..Project4` | **Рабочие слоты** текущей разработки. |

Схема работы (`scripts/conveyor.py`):
1. **Готовность к релизу** — три условия одновременно:
   * `STATE.json.completion_pct == 100` (чекбоксы `PLAN.md`);
   * **100% холодный код**: ни одного исходника с маркером `# HOT` / свежим mtime (<48ч);
   * **вердикт Владыки «ГОРЯЧИЙ»** в `reports/lord*.md`.
   Нет данных = нет релиза (VERIFICATION CONTRACT).
2. **Релиз**: рабочая папка переносится в `CompleteProjects/<проект>_<timestamp>/`,
   рядом пишется `ФИНАЛЬНОЕ_ДОСЬЕ.md` (состав, метрики кода/доков, структура,
   тесты, вердикт, история git, как попал в релиз).
3. **Очистка очереди**: выпущенный проект **удаляется из `Projects/`** — та же
   работа больше не повторяется.
4. **Заполнение слота**: освободившаяся рабочая папка получает следующий проект
   из очереди — **самый большой по количеству кода и документации**
   (метрика = строки кода + строки документации), копия делается с
   `cp -a --reflink=auto` (CoW, экономит место), рядом пишется `.queue_source`.
5. **Пополнение очереди**: если в `Projects/` не хватает проектов для слотов —
   берутся из каталога `QUEUE.json` (`queue[]`, по priority).

Команды:
```bash
python3 scripts/conveyor.py scan              # очередь, слоты, готовность, размеры
python3 scripts/conveyor.py run [--apply]     # прогон (hourly cron LV-promote-check, :10)
python3 scripts/conveyor.py claim Project1 cybertarot --apply   # вручную: взять проект в слот
python3 scripts/conveyor.py status            # манифест CONVEYOR.json
```
Манифест: `LivingCode/CONVEYOR.json` (слоты → проект, журнал выпусков).
Тест схемы: `scripts/test_conveyor.py` — 18 проверок на временном дереве
(релиз → удаление из очереди → выбор самого большого → копирование в слот →
идемпотентность → `[PROMOTION EVENT]` в журнале).
